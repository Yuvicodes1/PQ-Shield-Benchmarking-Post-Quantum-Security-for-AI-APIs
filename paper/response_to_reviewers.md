# Response to Reviewers

**Manuscript:** "Post-Quantum Signature Schedules for Streaming LLM Inference: A Measurement Study with PQ-Shield" (formerly "PQ-Shield: An Empirical Framework for Security–Performance Benchmarking of Post-Quantum Cryptography in Real-Time and Streaming AI Inference APIs")

We thank the reviewer for a careful and demanding review. It found a real inconsistency in our streaming timing data and several claims that went beyond the evidence. We ran new experiments where an experiment could answer a point, and narrowed the claims where it could not. Section and table numbers refer to the revised manuscript. All new results were collected on the same host as the original ones, with the same harness, and are regenerated by `python -m bench.paper_runs --steps 14-21` and `python -m analysis.paper_figures`.

## Summary of the main changes

1. **The streaming timing inconsistency is explained and measured (Section VI-C, Table V).** Per-signature time in a stream depends on the processor's power state, not on a measurement error. Every signing and verification call now records wall-clock and thread-CPU time.
2. **ML-DSA-65 key generation and signing are now validated** byte for byte against NIST ACVP vectors: 25/25 key generation and 30/30 signing, 130/130 vectors in total (Section VII, Table XV).
3. **A full man-in-the-middle (key-substitution) experiment** was run against the unauthenticated handshake. We also added an authenticated-handshake variant and measured its cost (Sections III-B, IV, VI-E; Tables VII–VIII).
4. **The stream-integrity evaluation now has 500 trials per cell**, with adaptive attacks on checkpoints, exact confidence bounds, and a false-rejection baseline (Section VI-D, Table VI). One adaptive attack defeated our previous client; we fixed it.
5. **Failed requests are diagnosed**, and a sensitivity analysis shows that excluding them does not change any conclusion (Section VI-H, Table XII).
6. **The weighted composite score is removed.** A weight-free dominance analysis replaces it, using cryptographic overhead versus the matched protocol and only the admissible concurrency levels (Section VIII, Table XVIII).
7. **Reframing.** The paper has a new title, abstract and contribution order led by the signature-schedule result. Key-establishment results are presented as confirmation of the prior TLS literature, and a structured "Limitations and Threats to Validity" section has been added (Section X).
8. **A new configuration, Hybrid-KEX-PQ (X25519MLKEM768 + ML-DSA-65),** is measured in the concurrency, streaming, checkpoint, threat and authentication experiments.

## Point-by-point responses

### 2. Methodological flaws

**2.1 Single-host confounding.** We agree, and we did not have a second host. We changed the claims rather than leave them standing:
- Equivalence is now claimed primarily at 10 connections, the setting least affected by contention.
- 1,000 connections is labelled throughout as a single-host stress test. Its differences versus Control-2RT are described as contention artifacts, not cryptographic effects.
- No configuration is ranked at 100 connections, and the decision analysis uses only 10 and 1,000.

The limitation is stated first under internal validity (Section X). A separate load-generator host is the first item of future work.

**2.2 Survivorship bias from failed requests.** The new Table XII breaks down every failure at 1,000 connections by stage and cause:
- All failures were connection resets (httpx `ReadError`). None were timeouts or HTTP errors, so the excluded requests were not slow requests that timed out.
- Control-2RT failed only on its first request. The protected configurations failed on both requests.

We repeated every comparison with each failed request counted at the 30 s client timeout, which is slower than any successful request. The cryptographic overhead changed by at most 0.17 s, and no equivalence verdict changed.

**2.3 / 3.5 / 4.2 Composite score.** The composite is removed. The reviewer was right on all three counts: it used overhead versus the single-request control, which is dominated by the protocol's extra round trip; it subtracted an assigned ordinal score from a ratio; and it counted cells we had disclaimed.

Table XVIII now lists three yes/no security properties of each construction and its measured costs:
- cryptographic overhead versus Control-2RT at 10 and 1,000 connections;
- handshake bytes;
- per-chunk signature bytes.

It then reports which configurations are dominated. The security properties now credit Hybrid-KEX's hedge: key establishment that survives an ML-KEM break, which classical configurations also have.

The result is that only Classical-RSA is dominated. Among the rest, moving up in security costs bytes, not latency, so no weighting is needed to state the trade-off. The "7 of 9 cells" claim is gone.

**2.4 Table VII / VIII timing inconsistency (table numbers of the previous version).** This was the most important point, and the reviewer was right that the data could not be reconciled as presented. We found and measured the cause (Section VI-C, Table V). A new diagnostic signs back to back, and once per 125 ms (the spacing of 5-token chunks). Each pattern runs idle, during Llama generation, with the core kept busy between calls, and confined to the efficiency cores.

| Pattern | ECDSA P-256 | ML-DSA-65 |
|---|---|---|
| Back to back, idle | 20 µs | 73 µs |
| Spaced 125 ms apart | 343 µs | 519 µs |
| Spaced, with the core kept busy between calls | 56 µs | 96 µs |
| Back to back, efficiency cores only | 132 µs | 386 µs |

Thread-CPU time tracks wall time in every pattern. The extra cost is therefore executed work on a clocked-down or slower core, not time spent waiting for the interpreter lock or the model's thread.

Inside real streams, the per-signature CPU cost of every streaming and checkpoint cell lies between the back-to-back and spaced costs: 100% of ECDSA cells and 95% of ML-DSA cells fall within ±20% of those bounds. The cost varies from run to run and between strategies with different signing rhythms, which produced the non-monotonic per-signature costs the reviewer identified. The re-run tables report wall-clock and CPU time side by side, and the model is now presented as giving bounds for time, not a point prediction.

**2.5 Unexplained residual.** The residual is now explained: it is the power-state effect above. The reviewer correctly noted that lazy OpenSSL initialization could not explain the liboqs residual. That explanation is now limited to a one-time cost, absorbed by the warm-up generation.

**2.6 Weak active-adversary model.** We agree that bit flips test the checks, not resistance to a man-in-the-middle. The new key-substitution experiment runs against a live server: the attacker replaces the key shares and signing key, either keeping the server's transcript signature or re-signing with its own identity key.
- **Unauthenticated handshake:** the attacker read every request and had a forged prediction accepted in all 1,800 trials (300 per configuration).
- **Authenticated handshake:** the server signs the handshake transcript with an identity key the client has pinned. All 3,600 substitution attempts were rejected at the handshake, and no genuine transaction was rejected.

Authentication costs one signature per handshake and 46–86 µs of client verification; end-to-end differences were not resolvable. The paper now states plainly that post-quantum key establishment does not stop an active attacker without authentication (Sections III-B, VI-E, IX).

**2.7 Thin attack statistics, no false-positive rate.** Each configuration–strategy–attack cell now has 500 trials, which pools to 3,000 per table entry. Every rate carries an exact Clopper–Pearson 95% interval: 3,000/3,000 means a lower bound of 99.88%.

False rejections were 0 in 750 genuine streams: 300 in the campaign plus 450 from the streaming sweeps, a 95% upper bound of 0.4%. The trials sample streams and attack positions on captured Llama streams, because detection is deterministic given the stream and the position; we say so in Sections V-I and X.

**2.8 Detection is not prevention.** We agree. Section VI-D now opens its second paragraph with "Detection is not prevention" and reports, for every detected attack, how many chunks the user had already been shown with no verified signature covering them. Without checkpoints, truncation is detected only at the end, after about half of a 100-token response (10.4 chunks on average) was shown unverified; reordering and dropping, after the whole response. Checkpoints reduce this to 8–9, 3–4 and 0.5 chunks at k = 10, 5 and 2 (Fig. 4b). The recommendations now tell clients to mark text as unverified until a signature covers it.

**2.9 ML-DSA signing not validated.** This is now closed. liboqs exposes no derandomized ML-DSA API, but all of its ML-DSA randomness comes from one replaceable source, `OQS_randombytes_custom_algorithm`, which is how liboqs runs its own known-answer tests. FIPS 204 key generation draws exactly the 32-byte seed ξ, and signing draws exactly the 32-byte value rnd. We supply each vector's bytes and check that liboqs drew exactly those bytes and no more.

This validates the same entry points the configurations use. The results are 25/25 ML-DSA-65 key generation (public and secret key) and 30/30 signing (15 deterministic, 15 hedged, with context strings), all byte for byte. Our earlier statement that this was impossible was wrong, and the paper says so.

**2.10 Network results stated without the lower-bound qualifier.** The abstract no longer quotes the network figure. Wherever the "about 5 ms" figure appears, it is now qualified as coming from the byte-level emulation and being a lower bound.

**2.11 Workload realism.** The title and abstract are scoped to streaming LLM inference, the workload we actually ran. External validity (Section X) lists the synthetic profiles, the single 3B model, and the single host class.

**2.12 Thermal drift.** No cross-configuration streaming time comparison remains. Table III's caption and Section VI-A say times are compared within a configuration only. The headline streaming numbers are signature bytes, which are exact, and within-configuration TTFT ratios.

### 3. Novelty

**3.1** We agree that the construction is not new and continue to say so. The contribution is now stated as the measurement of the signature schedule for post-quantum signatures on LLM streams, the exposure metric, and the adaptive-attack evaluation.

**3.2** Accepted. The abstract and contributions now lead with the signature-schedule result. Key-establishment equivalence appears as contribution 4, "Key establishment, as confirmation", and Section VI-H cites the TLS studies it confirms.

**3.3** The gap claim is softened to "among the studies we reviewed, we found none that…", with an explicit statement that the survey is not exhaustive. The related-work table's column is relabelled "Not covered (relative to this study)".

**3.4** "Framework" is removed from the title and the framing. PQ-Shield is described throughout as an application-layer emulation with an unauthenticated default handshake.

**3.5** See 2.3.

### 4. Unsupported claims

**4.1 Verification used to argue about signing.** The argument is rebuilt on server-side signing. ML-DSA-65 signing is 3.2× slower than ECDSA P-256 (67.9 vs 21.0 µs). That is about 47 µs per response back to back and about 180 µs per signature in a stream's spaced pattern, under 0.2% of a 92 ms transaction and not resolvable end to end. H4 is restated on that basis (Section VIII).

**4.2** See 2.3.

**4.3** Qualified on both axes: confidence bounds and false-rejection rates (2.7), and detection versus prevention (2.8). The claim now reads "every one of 135,000 trials of static and adaptive attacks". It also reports that, without the schedule check, checkpoint stripping went undetected in all 9,000 trials.

**4.4** The HNDL figure is described as a modeled byte volume, for one model and tokenizer, not information content. The threat model notes that response lengths already leak without a quantum computer, so the incremental HNDL harm is the plaintext content itself (Sections III-A, VI-G, X).

**4.5** The single-core generalization is removed. The paper reports only what was measured on the 8-core host: 3.5–4.8 cores, and 1.5% failures at 1,000 connections.

**4.6** "Matched exactly" is now restricted to signature counts and bytes. For time, the model is explicitly a bound (2.4).

**4.7** Classical-RSA is presented as a legacy worst case everywhere. The realistic classical baseline is Classical-ECDHE, and every equivalence and dominance claim is made against it. RSA is not in the abstract.

**4.8** Equivalence is now stated per configuration, with the exceptions:
- **10 connections:** all four ML-KEM configurations are equivalent to Classical-ECDHE.
- **1,000 connections:** Hybrid and Full PQC are equivalent; Hybrid-KEX is not shown equivalent; Hybrid-KEX-PQ is significantly faster, a contention artifact.

The equivalence table now distinguishes "no", "no (faster)" and "no (slower)", and marks the 100-connection rows as not interpreted.

## Code changes made during revision

- `crypto/instrumentation.py`: timers record thread-CPU time alongside wall time.
- `crypto/streaming.py`, `api/secure_streaming_client.py`: the client enforces the requested checkpoint schedule, and a missing checkpoint is a failure. This closes the checkpoint-stripping attack.
- `crypto/handshake_auth.py`, `api/secure_app.py`, `api/secure_client.py`: optional transcript signature under a pinned identity key.
- `crypto/hybrid_kex_pq.py`: the new configuration.
- `crypto/oqs_adapter.py`, `validation/nist_kat.py`: deterministic-randomness hook and ML-DSA key generation and signing vectors.
- `threats/key_substitution.py`, `threats/streaming_attack_campaign.py`, `validation/contention_check.py`: the new experiments.
- `analysis/paper_figures.py`: failure analysis, dominance table, timing, campaign, key-substitution and authentication-cost tables.
- `tests/test_review_round2.py` and `tests/test_nist_kat.py`: tests for all of the above.
